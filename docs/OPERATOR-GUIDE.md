# Operator guide

How to configure, deploy, operate and retire a **DEMO** mt5-gateway instance. Read
[KNOWN-LIMITATIONS.md](KNOWN-LIMITATIONS.md) first; this gateway is unfinished and unauthenticated
on its bridge.

Conventions: `<root>`, `<instance>`, `<broker>`, `<id>` and `<broker-server-alias>` are placeholders.
Run commands from the repository root unless a path says otherwise. Evidence status of every procedure
is stated; where a step is "not run against the current template", no container has ever been started
from `deploy/compose.instance.yml` as it stands today. The previous, pre-template compose file was run
in WO-MT5GW-0006 and WO-MT5GW-0008 (see [EVIDENCE-INDEX.md](EVIDENCE-INDEX.md)).

## 1. Prerequisites

- A host with Docker Engine and the Compose plugin. `mt5ctl lint` and `mt5ctl new` need only Python 3;
  `mt5ctl render` additionally runs `docker compose config` (use `--no-docker` to skip that).
- A broker **DEMO** account that you are entitled to use for automated access, and its login,
  password and server name.
- A built image with an explicit tag (never `:latest`). The skeleton tag `mt5-gateway:CANDIDATE-unbuilt-from-main`
  deliberately does not exist yet. Build from `main`:

  ```bash
  docker build -t mt5-gateway:<tag> .      # standard Docker build; not run in this effort
  ```

  The build is not hermetic: it downloads Wine, KasmVNC and noVNC at build time and the Dockerfile
  carries a stale `rc2` label. Treat the result as an unaudited candidate. Do not reuse `0.2.0-rc6`
  except as a rollback reference (see [ERRATA.md](ERRATA.md) E3).
- A shared broker-directory seed file, `servers.dat`, kept **outside** the repository (see section 5).

## 2. Directory layout (recommended)

```text
/srv/<root>/instances/<instance>/instance.yaml     # non-secret config (you edit this)
/srv/<root>/instances/<instance>/rendered/         # generated by mt5ctl render; gitignored
/srv/<root>/secrets/<instance>/                    # mode 0700; exactly three files, mode 0600
/srv/<root>/instances/_shared/servers.dat          # shared broker-directory seed, outside any repo
```

`secrets.dir` must be outside the repository and outside the instance's config directory (lint
refuses otherwise). Default peer discovery for the disjointness check looks at **sibling directories of
the instance directory** (those containing an `instance.yaml`, ignoring names starting with `_`), so
keeping all instance directories under one root makes lint compare them automatically.

## 3. Configure

```bash
tools/mt5ctl new /srv/<root>/instances/<instance> <instance>
```

- `<instance>` must look like `mt5-<broker>-demo-<id>`. `new` refuses anything else, including `live`.
- It copies `instances/_skeleton/instance.yaml`, replacing the example name and broker label. This also
  rewrites the name inside `network.name`, `data_volume` and `secrets.dir`.
- **You must still edit**: `broker_server` (skeleton value is a placeholder), `image` (placeholder
  tag), `servers_dat` and, usually, the base of `secrets.dir`. Lint will not notice a placeholder
  broker server that is syntactically valid.

Field-by-field rules are in [CONFIG-REFERENCE.md](CONFIG-REFERENCE.md). `broker_server` is the broker's
server **alias** as the terminal knows it (for example `<broker-server-alias>`), never an IP address or
host:port; lint rejects address-shaped values.

## 4. Provision secrets

The secrets directory holds exactly these three files, regular files (no symlinks), non-empty:

| File | Content | Mode |
|---|---|---|
| `mt5_login` | DEMO account login number, one line | 0600 |
| `mt5_password` | DEMO trading password, one line | 0600 |
| `vnc_password` | password for the browser UI (Basic Auth) | 0600 |

The directory itself must be mode 0700. Any other entry in the directory is a lint error.

```bash
install -d -m 0700 /srv/<root>/secrets/<instance>
for f in mt5_login mt5_password vnc_password; do
  install -m 0600 /dev/null /srv/<root>/secrets/<instance>/$f
done
# Fill each file with an editor (so the value never appears in shell history or process arguments):
$EDITOR /srv/<root>/secrets/<instance>/mt5_login      # and mt5_password, vnc_password
```

What the code does with them (`start.sh`):

- `mt5_login` / `mt5_password`: only the first line is read and surrounding whitespace is stripped.
  They are rendered into an MT5 start config on a **tmpfs** inside the container (`/run/gateway-secrets`,
  never the persistent volume) together with the non-secret server alias. If either file is missing or
  empty at container start, the terminal launches **without credentials** (a log line says so).
- `vnc_password`: becomes the password of the KasmVNC Basic Auth user `matt` (a fixed name in
  `start.sh`, not an operating-system account). If the file is missing or empty, or password
  provisioning fails, the UI starts **with no authentication at all** (the "fail-open" hazard H2).
  Lint requires the file to exist and be non-empty, but lint does not run in the container.
- Compose (non-Swarm) mounts secrets `root:root` mode 0400 whatever the compose file requests, so the
  unprivileged container user reads them through `sudo` (hazard H1).
- `start.sh` reads secrets once, at container start. After changing a secret, restart or recreate the
  container (section 8).
- An old `bridge_token` file is no longer part of the contract (removed in WO-MT5GW-0010). If an old
  secrets directory still contains one, lint fails with "unexpected entry"; the owner removes the file.

Do not echo, `cat`, log or paste secret values anywhere. Lint and render never read them.

## 5. Shared broker-directory seed

A fresh MT5 install only knows MetaQuotes' own demo servers; some brokers' servers are absent until the
terminal has a `servers.dat` that contains them (WO-MT5GW-0005/0006). `servers_dat` is a host path of a
seed file that is mounted read-only at `/seed/servers.dat` and copied into the terminal's `Config/` on
**first boot only**. It is never overwritten afterwards, so servers added later through the terminal
survive restarts. Keep the file outside the repository (lint enforces this). Lint does not check that the
file exists: make sure it does before `up`. How Docker behaves for a missing bind-mount source is not
verified here.

## 6. Lint and render

```bash
tools/mt5ctl lint   /srv/<root>/instances/<instance>/instance.yaml
tools/mt5ctl render /srv/<root>/instances/<instance>/instance.yaml
```

`lint` runs schema, cross-field, LIVE, secrets and peer-disjointness checks and exits non-zero on any
error. Add `--peers DIR/instance.yaml ...` to name peers explicitly (an empty `--peers` list means no
peers). `--skip-fs` skips secrets filesystem checks only (it is what CI uses on the skeleton).

`render` lints (including filesystem checks), writes `rendered/instance.env` (mode 0640, no secret
values), runs `docker compose ... config` and prints the plan, including the exact compose command. It
does not start anything. Use `--out DIR` to change the output directory.

## 7. Start, verify, operate (manual compose steps)

`mt5ctl` has **no** `up`, `down`, `status`, `logs`, `restart`, `verify` or `retire`. These are plain
Docker commands, and starting a credentialed instance is an owner-approved action (WO-MT5GW-0002 risk
acceptance: an explicit go before every credentialed start).

```bash
ENVF=/srv/<root>/instances/<instance>/rendered/instance.env

# start (add the overlay line only if ports.operator_ui is a number)
docker compose --env-file "$ENVF" \
  -f deploy/compose.instance.yml \
  -f deploy/compose.operator-ui.yml \
  up -d

docker compose --env-file "$ENVF" -f deploy/compose.instance.yml [-f deploy/compose.operator-ui.yml] ps
docker logs <instance> --tail 50
```

Every compose command for the instance needs the same `--env-file` and `-f` arguments (the template
uses required variables), including `stop` and `down`.

**Verify (what can be checked today, all manual and read-only).** There is no verify command; these
are the checks the historical work orders actually used.

| Check | How | Expected |
|---|---|---|
| Container health | `docker inspect -f '{{.State.Health.Status}}' <instance>` | `healthy` once up. First boot installs MT5 and Wine Python and took about 100 seconds in WO-MT5GW-0003; the healthcheck start period is 300 seconds. Health only means the terminal and bridge processes exist. |
| Startup progress | `docker exec <instance> tail -n 40 /tmp/start_sh.log` | steps `[1/12]` to `[12/12]`; credential lines say whether secrets were present, the UI line says whether Basic Auth is enabled |
| UI is gated | `curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:<port>/` | `401` (Basic Auth challenge). `200` without credentials means fail-open: see TROUBLESHOOTING |
| No unintended publication | `docker inspect -f '{{json .HostConfig.PortBindings}}' <instance>` | empty, or exactly one entry on a loopback address for container port 6901/tcp; nothing for 18812 |
| Broker connection | established sockets to external addresses inside the container (the WO-MT5GW-0006 method, reading `/proc/net/tcp` for state `01`) | at least one established external connection |
| Terminal API state | a read-only `initialize()` from a client on the instance network | `True`, `trade_mode` DEMO. Needs bridge access; see the warning below |

Warning on bridge access: the bridge is unauthenticated code execution. Reaching it needs a container
attached to the instance network (as WO-MT5GW-0006 did) or `docker exec`. Use it only for read-only
diagnostics, never leave a client attached, and make no order or modification calls. The client must use
`rpyc==5.2.3` (6.x is protocol-incompatible, WO-MT5GW-0002 Task 3b). Whether tick data is fresh has no
recorded check in this repository.

## 8. Restart and stop semantics

| Action | Command | Effect |
|---|---|---|
| Restart | `docker restart <instance>` | `start.sh` re-runs; the data volume keeps the Wine prefix and terminal, so install steps log "already installed" and the seed is not re-applied. This was proven in WO-MT5GW-0006 on the earlier deployment. Secrets are re-read. |
| Recreate | `docker compose ... up -d --force-recreate` | New container, same volume. Use this after changing a secret if your editor replaced the file (a single-file bind mount can keep pointing at the old inode; general Docker behaviour, not tested here). |
| Stop | `docker compose ... stop` | Stops the container, keeps it and the volume. |
| Down | `docker compose ... down` | Removes the container and the instance network; the named volume is **kept**. Never add `-v` except when retiring. |

**Stopping never closes positions or cancels orders.** Nothing in this repository sends order calls on
stop; positions and pending orders live at the broker and persist, including broker-side SL/TP. A
stopped instance cannot manage them. There is no graceful-shutdown logic: `start.sh` has no signal
handler, and the template sets no stop grace period, so Docker's defaults apply. Clean terminal
shutdown on stop is not verified.

Restart policy comes from `restart` in `instance.yaml` (default `no`). With `no`, a host reboot or
Docker daemon restart leaves the instance down until someone starts it. `unless-stopped` is allowed by
the schema but has not been exercised on this template. (From the code: the container's watchdog exits 0
when all Wine processes are gone, so `on-failure` would not restart that case.)

After any restart, treat state as unknown until you have looked at the broker: there is no reconcile
tooling here.

## 9. Add a second DEMO account (zero source edits)

1. `tools/mt5ctl new /srv/<root>/instances/<instance-2> <instance-2>` (a different name, for example a
   different `<id>`).
2. Edit only that new `instance.yaml`: `broker_server`, `image`, `servers_dat`, `secrets.dir`, and a
   **different** `ports.operator_ui` (or `none`).
3. Create `/srv/<root>/secrets/<instance-2>/` with its own three files (never reuse another
   instance's secrets directory).
4. `mt5ctl lint` (peers are the sibling instance directories, so collisions on project, container,
   network, volume, secrets directory or published port are errors) and `mt5ctl render`.
5. Start it with its own `rendered/instance.env`, exactly as in section 7.

This is proven at the configuration level only: `tests/test_two_instances.py` shows two configs are
disjoint, that `docker compose config` renders disjoint names, networks, volumes, secret files and
loopback ports, and that no application source file changes. Two containers have not been run side by
side from this template. Disjointness is checked between configs, not against Docker's actual state
(`docker volume ls`, `docker network ls`, listening ports).

## 10. Retire an instance

There is no `retire` command. All steps are manual and destructive steps need the owner's explicit go.

1. Confirm at the broker (not through this gateway) that the account has no open positions or orders
   you care about. Stopping does not close them.
2. `docker compose ... down` (keeps the volume).
3. Optionally remove the data volume (`docker volume rm <data_volume>`): this deletes the Wine prefix,
   the MT5 install, terminal config and logs. The gateway keeps no authoritative trading state, but
   anything you did in the terminal UI is lost.
4. The owner securely removes the secrets directory. Tooling never deletes secrets.
5. Archive or delete the instance config directory (it contains no secrets). Free its port and name.

## 11. Things not to do

- Do not publish container port 18812, put it on a host interface, or attach other workloads to an
  instance network.
- Do not set `operator_ui` to anything reachable from a network; lint allows loopback only. Use an SSH
  tunnel for remote access. The UI is cleartext HTTP.
- Do not use real-money credentials. There is no in-container guard; the terminal logs into whatever the
  secrets open.
- Do not edit `docs/evidence/`; add corrections to [ERRATA.md](ERRATA.md).
